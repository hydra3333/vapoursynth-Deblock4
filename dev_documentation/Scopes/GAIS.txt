To clarify "Instruction Poisoning," we are specifically talking about the **AVX-SSE Transition Penalty**. This is a hardware-level performance trap that occurs when a CPU switches between legacy SSE instructions and modern AVX/AVX2 instructions.

In the context of your Deblock4 filter, this is a "silent killer" that can make your AVX2 code run slower than your scalar code if not handled correctly.

---

### 1. What is Instruction Poisoning (AVX-SSE Transition)?
Intel and AMD CPUs have 256-bit registers (YMM) for AVX. The lower 128 bits of these registers are shared with the legacy SSE registers (XMM).

*   **VEX Encoding:** AVX instructions use a new prefix (the "v" in `vaddps`). This tells the CPU to treat the registers as 256-bit and, crucially, to zero-out the upper 128 bits if the operation only uses the lower 128 bits.
*   **Legacy Encoding:** SSE instructions (like `addps`) do not know about the upper 128 bits. When you execute a legacy SSE instruction, the CPU must preserve the upper 128 bits of the YMM register.

**The "Poison":** If your AVX2 code (which has "dirtied" the upper 128 bits of the registers) is suddenly followed by a legacy SSE instruction, the CPU incurs a **massive penalty (up to 100+ cycles)** to save the state of those upper bits. This transition can happen if:
1.  You call a standard library function (like `memcpy`) that was compiled with legacy SSE.
2.  Your Zig code dispatches from an AVX2 function back to a generic helper function that the compiler lowered to legacy SSE.
3.  The compiler "accidentally" mixes `v`-prefixed and non-`v` instructions in the same block.

---

### 2. The Solution: `VZEROUPPER`
The "antidote" is the `VZEROUPPER` instruction. It tells the CPU: *"I am done with the upper 128 bits of all YMM registers; you can wipe them and return to a clean SSE state."*

**The Rule:** You must call `VZEROUPPER` at the end of every AVX2/AVX function before returning to the "main" app logic or calling any non-AVX functions.

---

### 3. Recommended `build.zig` Configuration
In Zig, you want to ensure that when you are building your AVX2 "tier," the compiler knows it is **allowed** to use the VEX prefix for everything.

Since you are building a VapourSynth DLL that dispatches at runtime, you usually cannot just set one global CPU target. You need to handle "feature-aware" compilation.

#### Option A: Target-Specific Modules (Recommended)
The cleanest way is to define your SSE4.1 and AVX2 logic in separate files and tell `build.zig` to compile them with those specific CPU features enabled.

```zig
// Example build.zig snippet
const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    const lib = b.addSharedLibrary(.{
        .name = "vapoursynth_deblock4",
        .root_source_file = b.path("src/main.zig"), // Your dispatcher is here
        .target = target,
        .optimize = optimize,
    });

    // 1. Define the AVX2 "tier"
    // We create a specific target query for AVX2
    const avx2_target = b.resolveTargetQuery(.{
        .cpu_arch = .x86_64,
        .os_tag = .windows, // or .linux
        .cpu_features_add = std.Target.x86.featureGroup(.avx2),
    });

    // 2. Add the AVX2 implementation as a separate module or file
    // This ensures LLVM knows it can use VEX (v-prefix) instructions here
    const avx2_impl = b.addModule("deblock_avx2", .{
        .root_source_file = b.path("src/deblock_avx2.zig"),
        .target = avx2_target,
        .optimize = optimize,
    });
    
    lib.root_module.addImport("deblock_avx2", avx2_impl);
    
    b.installArtifact(lib);
}
```

#### Option B: Inline CPU Feature Switching

```zig
pub fn process_avx2(pixels: []u8) void {

}
```

To avoid "Instruction Poisoning" and R76-style edge failures:

1.  **VEX Prefixing:** By using `b.resolveTargetQuery` with `.cpu_features_add = std.Target.x86.featureGroup(.avx2)`, you ensure LLVM emits `v`-prefixed instructions. This makes the code "AVX-native."
2.  **The Antidote:** Ensure your AVX2 entry points call `vzeroupper` (via `asm volatile`) before returning control to the VapourSynth core.
