### Why this Scope is Highly Effective for an AI Coder

1. **The Two-Record Model (B1):** Keeping `Actual` and `Effective` capabilities separate is an excellent design choice. It prevents the debug force-down seam from mutating the global hardware state, ensuring that diagnostics can always report the physical truth alongside the overridden behavior.
2. **The Provenance Model (B7):** Explicitly tracking `detected_present`, `detected_absent`, and `policy_assumed_present` resolves the issue of checking kernel-only OS-state registers (like CR4 for `OSFXSR` and IA32_EFER for `SCE`) from a user-mode DLL, while still documenting the Windows x64 baseline.
3. **The One-Way Dependency Rule & Sweep Test (2.6):** This enforces strict architectural boundaries. Preventing the production core from referencing scaffolding or temporary markers guarantees that the transition to the final filter stages will be clean and free of circular dependency issues.
4. **Comptime Membership Assertion (B6):** Checking manual bit-detection lists against Zig's `std.Target.x86` CPU levels at compile time is a great guard against microarchitecture drift when upgrading Zig versions.
5. **The First-Class Self-Test Executable (2.5):** Compiling a permanent verification executable from the same source graph ensures that capability testing is robust and easy to verify without needing to load the DLL into a VapourSynth host during early development stages.

### Key Implementation Guidance for the Coder

To ensure the AI coder implements the design exactly as intended without introducing silent drift, the following three implementation patterns should be emphasized during execution:

#### A. Implementing Thread-Safe Once-Semantics (5A)
In Zig 0.16.0, the standard way to implement thread-safe, lazy initialization is `std.Thread.Once` (under `std.Thread`). The coder should utilize it for `detectActualOnce()` like so:

```zig
const std = @import("std");
var global_actual: ActualCapabilities = undefined;
var actual_once = std.Thread.Once{};

fn runDetection() void {
    global_actual = performDetectionProcedure();
}

pub fn detectActualOnce() *const ActualCapabilities {
    actual_once.call(runDetection);
    return &global_actual;
}
```

#### C. Verification of Inline Assembly Constraints (3.5)
The non-normative inline assembly block provided in the scope is well-formed for LLVM under x86-64. The coder should ensure that register constraints are mapped exactly to `eax`/`ebx`/`ecx`/`edx` as shown, because LLVM handles the callee-saved preservation of `rbx` under Win64 automatically when `ebx` is declared as an output constraint.
