## 3. The current probe cannot settle `vzeroupper`

This is the main technical concern.

`src/backend_probe_avx2.zig` contains only a no-argument marker returning a constant `u32`. It performs no vector or floating-point work and is very unlikely to emit any AVX/YMM instruction.

The scope simultaneously:

* forbids changing the marker function;
* forbids adding backend/kernel logic;
* requires Stage 1B.2 to settle `vzeroupper` by inspecting the v3 object.

With no AVX/YMM-producing code, absence of `vzeroupper` proves only that none was required in this trivial function. It does not prove how the compiler handles an AVX-using function returning to SSE/baseline code.

A designer ruling is required:

### Option A — defer the proof

Stage 1B.2 records:

```text
No AVX/YMM instruction was emitted by the current constant-return probe;
therefore no AVX-to-SSE transition existed and `vzeroupper` was not applicable.
The compiler-transition proof is deferred to the first real v3 function that
actually uses YMM state.
```

### Option B — amend the scope to permit a dedicated probe

Permit a narrowly bounded, non-executed AVX/YMM code-generation probe designed specifically to make the compiler produce an AVX ABI boundary. Its retention and inspection method would also need to be specified.

Under the current permitted/forbidden changes, Option B cannot be implemented safely without further scope design.

W3C recommends **Option A** unless W3D has a clean dedicated-probe design.

## 4. Toolchain-resolved features must not automatically become runtime checks

Part 3.3 asks the report to record:

1. the exact feature set reported by the toolchain for each model; and
2. the complete feature list that Stage 1B.3 must verify at runtime.

These are not necessarily identical sets.

A Zig CPU model's resolved feature set may include compiler code-generation or tuning properties in addition to hardware/OS capability bits. Stage 1B.3 cannot CPUID-check a compiler tuning property.

The report should therefore distinguish at least:

```text
A. Authoritative psABI level membership
   Runtime-checkable CPU/OS requirements belonging to v1/v2/v3.

B. Separate runtime AVX state requirement
   OSXSAVE and XGETBV/XCR0 XMM+YMM enablement.

C. Zig resolved target/model feature set
   Including any compiler-internal or tuning properties; recorded for
   reproducibility but not automatically imposed on the runtime guard.
```

Please confirm that Part 3.3 does **not** instruct Stage 1B.3 to test every bit appearing in Zig's resolved model feature set.

## 1. BLOCKER — OSXSAVE is simultaneously included in and excluded from the v3 level

Part 2 correctly states that the full `x86_64_v3` level includes:

```text
AVX, AVX2, BMI1, BMI2, F16C, FMA, LZCNT, MOVBE, OSXSAVE
```

Part 3.3 then places `OSXSAVE` in set B and states that it is:

```text
not a level member
an OS-state check, not a CPUID feature-membership bit
```

Those two statements cannot both be true.

W3X has explicitly restated that the tiers are the complete x86-64 psABI microarchitecture levels and that the named level is the authoritative feature contract. The scope itself repeats that this is settled and must not be independently reinterpreted.

Please obtain or record W3X's correction.

The correction that appears consistent with charter G3 and README 12.3 is:

```text
A. AUTHORITATIVE psABI LEVEL MEMBERSHIP

   x86_64_v3 includes OSXSAVE as a named-level member.

B. SEPARATE RUNTIME AVX/YMM OS-STATE REQUIREMENT

   XGETBV/XCR0 must show XMM and YMM state enabled before executing AVX-family
   backend code.

   This XCR0 state requirement is additional runtime safety; it is not itself
   another psABI feature-level member.
```

Consequently, Stage 1B.3 would verify complete set A, including OSXSAVE for v3,
and then separately verify the XCR0 state requirement in B.

W3C will not implement or silently infer this correction without a revised scope
or explicit W3X ruling.

## 2. The v1 classification obligation is still under-specified in the automated gate

Part 3.1 correctly names four inspection inputs:

```text
generic -> v1
scalar  -> v1
sse41   -> v2
avx2    -> v3
```

It also correctly says both v1 objects must contain nothing above
`x86_64_v1`.

However, the fallback classifier examples and the definition-of-done
parenthetical focus on:

```text
no AVX-512 anywhere
no VEX/AVX in v1 or v2
```

Absence of VEX/AVX is not sufficient to classify an object as v1. A v1 object
must also contain no instruction whose minimum contract is v2 or higher.

Please amend Part 3.1, V4 and the checklist to require:

```text
- v1 objects: no instruction requiring x86_64_v2, v3 or later;
- v2 object: no instruction requiring x86_64_v3 or later;
- v3 object: no instruction requiring a level above x86_64_v3.
```

The automated portion may remain a conservative deny-list, provided:

```text
- it covers every reliably detectable forbidden family appropriate to each
  object;
- complete disassembly is retained;
- remaining classification is explicitly manual;
- the batch/report does not claim exhaustive automated classification.
```

The current four-object design is correct; only the stated gate obligation
needs tightening.
