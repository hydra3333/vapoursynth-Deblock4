RESEARCH REQUEST FOR GAIS - Zig 0.16.0 conditional module import at file scope

CONTEXT

We are building a Zig 0.16.0 project (a VapourSynth plugin, dynamic library).
It has a debug-only "force-down" test seam whose code MUST NOT EXIST in a
release binary - not merely be unreachable, but be genuinely absent (no machine
code, no symbols, no strings). The seam is gated by a build option
(b.addOptions -> imported options module -> comptime-known boolean, e.g.
build_options.enable_force_down).

The seam's implementation lives in its own source file (a separate module),
e.g. force_down_debug.zig, imported with @import.

We have established (and will separately verify) that a comptime-false
`if (build_options.enable_force_down) { ... }` around a STATEMENT causes the
untaken branch not to be analyzed, so code and imports inside it are omitted
from a release binary.

THE PROBLEM WE WANT SOLVED

We want the conditional import declared ONCE, at the TOP of the file, in the
conventional place where imports live, so it is clearly visible as a
conditional dependency - AND usable from MULTIPLE gated sites lower in the file
without each site repeating the @import.

Two shapes we already understand, and their drawbacks:

  Shape 1 - plain top-level import, use gated:
      const fd = @import("force_down_debug.zig");   // unconditional import
      ...
      if (build_options.enable_force_down) {
          eff = fd.applyMaskOnly(actual);
      }
    Drawback: the import is UNCONDITIONAL and sits at the top looking like a
    normal dependency; omission then relies on the module's own internals being
    conditional (e.g. a conditional-namespace `pub const tools = if (enable)
    struct {...} else struct {};`). The top-level import line itself gives no
    visual signal that it is debug-only.

  Shape 2 - import inside the gate:
      if (build_options.enable_force_down) {
          const fd = @import("force_down_debug.zig");
          eff = fd.applyMaskOnly(actual);
      }
    Drawback: `fd` is block-scoped to that one `if`. If the seam is used at
    SEVERAL places in the file, EACH gated block must repeat its own
    @import. There is no single shared conditional binding.

We also understand that the top of a Zig module is DECLARATIONS ONLY - you
cannot place a bare `if (...) { ... }` statement at file scope - so "wrap an if
around the import at the top" is not directly expressible the way C's
`#ifdef ... #include ... #endif` is.

QUESTIONS FOR GAIS (Zig 0.16.0 specifically; cite version-specific behaviour)

1. Is there an idiomatic way to declare a SINGLE, file-scope, CONDITIONAL
   import that:
   (a) appears at the top of the file in the conventional import location,
   (b) is visibly conditional (a reader can see it is debug-only),
   (c) resolves to the real module when the option is true and to something
       inert when false,
   (d) is usable from multiple sites below WITHOUT re-importing, and
   (e) causes the real module's code/strings/symbols to be genuinely OMITTED
       from a release binary when the option is false?

2. Specifically, does the conditional-DECLARATION form work and satisfy (e)?
       const fd = if (build_options.enable_force_down)
           @import("force_down_debug.zig")
       else
           struct {};   // or `void`, or an empty stub - please advise which
   That is: a top-level `const` bound to a comptime `if` whose true branch is
   @import and whose false branch is an empty namespace. Does Zig, in release
   (option false), genuinely NOT analyze or emit the real module in this form,
   or does binding `@import` in a conditional declaration still pull the module
   into the compilation? Is a conditional DECLARATION treated the same as a
   conditional STATEMENT for omission purposes, or differently?

3. If `else struct {}` is used, what happens at the USE sites? Presumably each
   use is still wrapped in its own `if (enable)` so the empty-struct branch is
   never reached in release; but does merely having `fd` bound to `struct {}` at
   file scope, referenced only inside comptime-false gates, keep the binary
   clean? Confirm there is no residual symbol or string from the disabled
   module. What is the recommended false-branch value - `struct {}`, `void`, an
   empty stub module, or something else - to make stray references fail to
   compile (a desirable structural boundary) while keeping release clean?

4. Is there a BETTER-established Zig 0.16 idiom for "conditionally-compiled
   optional dependency used in several places" that we have not considered?
   For example:
     - a wrapper module that itself is either the real thing or an empty stub,
       selected in build.zig (so the SOURCE always imports the same name but the
       build graph decides which file backs it);
     - build.zig choosing between two files for the same import name via a
       module alias / dependency;
     - anonymous import / addAnonymousImport tricks;
     - or any pattern the Zig community treats as standard for optional debug
       modules.
   Please describe the cleanest option and why, with a minimal build.zig +
   source example for Zig 0.16.0.

5. For each viable approach, state explicitly whether it delivers TRUE OMISSION
   from the release binary (no symbol, no string, no machine code) or only
   unreachability, and how one would PROVE absence by binary inspection
   (symbols / strings / disassembly).

DELIVERABLE

A recommendation with rationale, a minimal Zig 0.16.0 example (build.zig plus
source), and an explicit true-omission vs unreachability verdict for the
recommended approach. Please show reasoning and cite Zig-0.16-specific
behaviour rather than giving a bare answer, as this will be compared against an
independent coder finding and an empirical compile test.
